# TransformerArchitectureCustom

A decoder-only (GPT-style) transformer built from near-scratch (numpy only, no ML framework) — the first concrete step toward LLM-shaped TCA segments. The goal here is a fully understood, fully modifiable baseline: every operation (projections, per-head attention scores, masking, softmax, residual adds) is a separate, inspectable step rather than one opaque framework call, so "custom manipulation of architecture internals" has something real to diverge from, and tracing hooks have real sub-layer boundaries to attach to.

## Status: working, gradient-verified, confirmed to actually learn

- **`layers.py`** — core primitives (`Linear`, `LayerNorm`, `Embedding`, `GELU`, `softmax`, `cross_entropy_loss`), each with manual forward + backward. Same discipline as TCA's `ProcessingNode`: forward caches what backward needs, backward accumulates parameter gradients.
- **`attention.py`** — `MultiHeadSelfAttention`, causal-masked (decoder-only). Q/K/V projections, per-head scaled dot-product scores, masking, softmax, and the output projection are all separate steps — this is the main surface meant to be swapped/modified later.
- **`transformer.py`** — `FeedForward`, `TransformerBlock` (pre-norm residual: `LN → attn → +x`, `LN → ffn → +x`), and `GPTStyleTransformer` (token + positional embedding → N blocks → final LN → output head → cross-entropy).
- **`trace.py`** — `TraceRecorder`: opt-in per-sublayer recording (attention weights per head, Q/K/V/output norms, FFN activation norms), dumped to JSONL. A *new* schema, not the existing `visualizer/`'s `trace.jsonl` — that one is geometric/segment-routing-specific (node positions, signal paths) and has no notion of layers or attention heads. Includes a quick attention-entropy summary (per-head mean entropy of the attention distribution) as a first cheap interpretability signal.
- **`grad_check.py`** — numerical (finite-difference) gradient checks for every layer in isolation, including `MultiHeadSelfAttention`. All pass to float-precision (~1e-8).
- **`grad_check_full_model.py`** — end-to-end check on the *composed* model (embeddings → 2 blocks → final LN → head → loss), catching wiring mistakes at residual/composition boundaries that per-layer checks can't see (e.g. a dropped or double-counted gradient contribution across a residual add). All pass (~1e-7).
- **`train_toy.py`** — the real test: a synthetic delayed-copy task (`token[i] = token[i-k]`, which requires genuine attention to a fixed offset, not just a per-position bias) trains from random-guess loss (`ln(vocab_size)`) down to a real fit, with **100% held-out accuracy** on determined positions. The attention-entropy trace already shows interpretable structure — layer-0 heads specializing (lower, more varied entropy) vs. layer-1 heads more diffuse.
- **`train_tiny_with_logging.py`** — confirms the LOGGING INFRASTRUCTURE itself (not just the model) survives real training: `TraceRecorder.reset()` actually empties state between dumps (no leakage across steps), the JSONL file accumulates one well-formed entry per logged step, and every parameterized layer — including the ones with no forward-activation tracing, like embeddings/LayerNorms/the output head — gets a per-step weight-update record (`sgd_step(lr, trace=...)`: grad norm, update norm, weight norm, ratio, one per (layer, param) pair, derived from the model rather than hardcoded so a newly-added layer going untraced fails loudly).

## A real baseline test: char-level language modeling on tiny-shakespeare

Everything above validates *correctness* on synthetic toy tasks. This is different: a real benchmark, compared against a **published reference number**, not a toy sanity check — specifically scoped because pure NumPy/CPU is nowhere near competitive with real LLM quality at any real scale (see Design notes), so "compare to other LLMs" had to mean something tractable: match a known small from-scratch transformer's parameter count and step budget on the same real corpus, and see where we land.

- **`tokenizer.py`** — `CharTokenizer`, character-level (not BPE — avoids building merge-training infrastructure for what's meant to be a baseline harness, not a tokenizer project; char-level LM on tiny-shakespeare is itself a standard, recognized benchmark mode).
- **`optim.py`** — `Adam` + a linear-warmup/cosine-decay `lr_schedule`, generalized to any model exposing `all_sublayers()`. Added because the fixed-LR SGD used everywhere else in this project is unlikely to converge well enough, in a tractable step budget, to be a meaningful comparison. Sanity-checked (`optim_sanity_check.py`) by minimizing a convex quadratic with a known optimum — there's no backward pass to gradient-check here, so this checks the update rule itself (sign errors, bias-correction bugs) instead.
- **`data/tinyshakespeare.txt`** — the standard ~1.1MB corpus (Karpathy's char-rnn/nanoGPT example), fetched directly via `curl` (not `WebFetch`, which AI-summarizes content rather than returning raw bytes).
- **`train_tinyshakespeare.py`** — model sized to 826,368 params to match nanoGPT's own reported ~0.83M-parameter reference point as closely as practical (vocab_size=65 for both, confirmed), trained for the same 3000 iterations.

**Result (one run): val loss 1.5429, vs. the nanoGPT reference's 1.7236 at matched param count and step count** — meaningfully *better*. Honest caveats: single run, not averaged over seeds (unlike the multi-seed rigor used for other ablations in this project — a 90-minute-per-run cost on CPU made that impractical here); hyperparameters don't exactly match the reference (no dropout here, possibly different batch size/LR schedule in theirs), so some of the gap could come from those differences rather than pure implementation quality; training had plateaued by step ~2200–3000 (val loss noisy around 1.54–1.56), consistent with being near convergence for this config, so stopping at 3000 to match the reference wasn't an early/lucky cutoff.

A real, measured performance fix came out of preparing for this run: profiling showed `GELU`'s `x**3`/`x**2` (generic NumPy integer power) was ~14x slower than the mathematically identical `x*x*x`/`x*x` on this NumPy build, accounting for ~58% of total step time before the fix — found via `cProfile`, not assumed, and confirmed with a direct microbenchmark before touching the shared `layers.py` file. Cut the full run from an estimated ~121 minutes to ~95 minutes. All gradient checks re-verified afterward (identical formula, just computed differently — no new correctness risk, confirmed, not assumed).

## DistributionJudge: TCA's JudgeNode concept, repurposed

TCA's `JudgeNode` clusters the input feature space (k-means) to pick which segment handles a sample — a router. `judge.py`'s `DistributionJudge` keeps "cluster the space the model operates in" but repurposes the output: cluster membership becomes a **novelty signal** (how far is this input from anything the model actually trained on), not a routing decision. Fit once, post-training (mirroring `ArchetypeRouter`'s fit-after-the-fact pattern in TCA — representations drift during training, so fitting mid-training describes a model that no longer exists by query time), via `sklearn.cluster.DBSCAN` over the **last-token final hidden state** (the exact vector the output head predicts from) across the training set.

- **`judge.py`** — `fit()`, `query()`/`query_batch()` (nearest-training-point distance + that point's cluster label, or noise), `cluster_population_summary()` (a direct report of what the training set's activations were concentrated on — bias visibility, for free), `cluster_members()`/`nearest_training_examples()` (attribution: "what training inputs does this one's activation most resemble").
- **`judge_smoke_test.py`** — standalone check against synthetic data with known ground truth (3 clean blobs + a deliberate out-of-distribution point) before trusting it against real model activations, where "is this behaving correctly" would be much harder to tell apart from "is the model doing something unexpected." All pass.
- **`confidence.py`** — `ConfidenceEstimator`: same shape as TCA's (`predicted_error = softplus(dot(w, features)+bias)`, trained against real absolute error, not squared — TCA hit a saturation bug doing that), generalized from TCA's fixed 2 features to an arbitrary feature vector so a clean with/without-novelty ablation is possible. Gradient-checked (~1e-11).
- **`judge_confidence_test.py`** — the actual question: does the Judge's novelty distance help predict how wrong the model will be, beyond the model's own raw softmax confidence? Tested, not assumed: train the delayed-copy model on in-distribution sequences only, build a held-out mix of in-distribution and out-of-distribution (unstructured random-token) sequences, fit two `ConfidenceEstimator`s (surprise-only baseline vs. surprise+novelty), compare held-out error-prediction accuracy. **Result (one run): 27% lower held-out MAE, correlation with actual error 0.36→0.62.** The underlying reason is a real, known failure mode the test surfaces concretely: the model's raw softmax barely reacts to out-of-distribution input (surprise 0.012→0.155) even though its actual error explodes (loss 0.012→3.91) — classic neural-net overconfidence on OOD input — while the novelty distance separates the two regimes almost perfectly (0.000 vs 2.456). Caveat: this was an "easy" OOD case (fully unstructured vs. a clean rule); a subtler distribution shift (e.g. a different delay) would be a tougher test and likely shows a smaller effect — not yet run.

## Sparse Mixture-of-Experts (SMoE)

**The mechanism**: a normal transformer block applies the same FFN to every token. SMoE replaces that single FFN with several smaller "expert" FFNs plus a small gate (a linear layer) that scores each expert per token; the top-k (here, top-1 or top-2) experts are selected, their outputs combined via a softmax-normalized weighted sum over just the selected ones. This lets total model capacity grow (more experts) without growing compute per token proportionally (each token only touches a few experts' worth of FFN work). The gate's selection is a hard, discrete choice, so vanilla gradient descent only ever reaches the logits of experts that were *actually picked* for a given token — left alone, this causes gate collapse (whichever expert gets picked early gets trained more, gets better, gets picked more). The fix, implemented here, is a Switch-Transformer-style auxiliary load-balancing loss added during training — the *only* gradient path that reaches unselected experts' logits.

- **`moe.py`** — `SparseMoEFeedForward`: drop-in replacement for `FeedForward` (identical `forward(x, trace=None)`/`backward(dout)`/`named_sublayers()`/`zero_grad()` contract, so `TransformerBlock` doesn't need to know which one it's holding). Honest simplification stated directly in the module docstring: this computes *every* expert's output for *every* token (dense compute), then zeros non-selected experts' contribution via the gating weights — the real math of sparse gating (top-k selection, the backward-pass asymmetry between selected/unselected experts, the load-balancing loss), not the compute saving a production implementation would get from actually skipping unselected experts.
- Also supports an **optional per-cluster gate bias** sourced from an attached `DistributionJudge` (`attach_judge()`) — "inputs like this cluster have tended to do better on expert N." This is **not** gradient-trained; it's updated via `update_judge_bias_credit()`, a proportional-credit rule matching `ArchetypeRouter`'s (nudge toward whatever beat a per-cluster running-average loss, not a hard assignment) — a second, independent correction channel on top of the learned gate.
- **`moe_grad_check.py`** — found and fixed a real lesson, not a bug in `moe.py` itself: `backward()` *always* bundles in the aux-loss gradient (correct — that loss genuinely contributes to the total objective every real training step), so a gradient-check target function that only measures the output-weighted loss is checking a *different* scalar than `backward()` actually differentiates, and will show a spurious mismatch. Fixed by including `aux_loss_weight * last_aux_loss` in the checked scalar. Both paths (primary + aux, and aux in isolation) now pass exactly (~1e-11).
- **`grad_check_moe_model.py`** — same lesson applied at the full composed-model level (2 independent MoE blocks): passes exactly once every block's aux-loss term is included in the checked scalar. Also confirms different blocks' expert weights are genuinely independent objects, not accidentally aliased.
- **`moe_specialization_test.py`** — "each layer has its own independent experts" (Option A, chosen over "tokens route through different *blocks themselves*" (Option B) as the first, smaller step — see commit history for that discussion): confirms (1) the MoE-wired model still hits 100% held-out accuracy on the delayed-copy task, matching the dense-FFN bar; (2) the aux loss measurably reduces expert-usage imbalance (1.09x vs. 1.47x max/mean ratio without it, in one run — modest but real on this easy task); (3) the two layers' gates route tokens with only 35.2% agreement (chance level for 4 experts is 25%) — clearly not copying each other's decision, but not fully uncorrelated either, which is plausible since both layers see representations of the same underlying input.
- **`moe_judge_bias_test.py`** — does the Judge-conditioned gate bias mechanism (`attach_judge()`/`update_judge_bias_credit()`) actually do anything, confirmed with a Judge fit on block0's per-token FFN-input activations (not the final-hidden-state Judge used for confidence — a different vector, needs its own Judge instance): (1) the bias table measurably moves away from zero after real credit-update rounds using per-token loss (total movement 3.18 in one run); (2) that movement actually changes real routing decisions (13.5% of held-out tokens routed differently with the bias vs. with it temporarily disabled); (3) 9/11 clusters developed a distinct, non-trivial per-expert preference. **What this does NOT yet establish**: whether the shifted routing actually reduces loss — that's a separate ablation (same rigor as `judge_confidence_test.py`'s), not yet run (see Next steps).

## DCST comparison and the resulting hybrid (Tiers 1–3)

After building the above, compared it against a separate research proposal in this repo (`Data-Clustered Sparse Training Across All Layers.md`, "DCST") that starts from the same root intuition — cluster training examples by representation, use that structure to organize computation — but reaches for something bigger: data clusters directly **replace** the learned router (no gate at all), span FFN+attention+conv from one shared cluster map, and the whole point is real sparse-compute savings. What we'd built is structurally closest to DCST's own baseline **#10, "cluster-initialized learned router"** — data structure as a prior nudging a still-learned gate, not replacing it. Full comparison table in commit history; three concrete, scoped pieces of DCST were pulled in after that comparison:

**Tier 1 — validating the mechanism itself, DCST's way.** DCST's central methodological tool is the **shuffled-cluster control**: identical mechanism, but cluster labels randomly permuted (same sizes preserved) — isolates "does the real data structure matter" from "would any same-sized partition do just as well." Ran this (`moe_dcst_ablation.py`) as a 4-way comparison, all continuing from the IDENTICAL warmed-up model (same rng seed replayed deterministically, no checkpoint machinery needed): no-bias baseline, real-Judge bias (zero-init), real-Judge bias (DCST-style strong prior-init — §4.3.1, cluster k starts biased toward expert k, credit updates free to drift), and the shuffled control.

**Result (one run, delayed-copy task): baseline=0.1724, real-zero=0.1727, real-prior=0.1724, shuffled=0.1763.** Honest reading: neither real-cluster config beats the no-bias baseline — the task is likely too easy/saturated by the warm-up point (100% accuracy, loss already near floor in all four) to leave headroom for the mechanism to show a benefit either way. But the **shuffled control is measurably worse** than both the baseline and the real-cluster configs (-2.3%) — i.e., real clusters are at worst neutral, while an arbitrary same-sized partition is mildly *harmful* (injects routing noise ungrounded in anything real). This lands close to one of DCST's own anticipated outcomes (§6, "DCST ≈ shuffled control"), just with a sharper edge: real ≈ baseline > shuffled, not real ≈ shuffled. Separately, DCST-style prior-init did edge out zero-init (0.1724 vs 0.1727) — consistent with their reasoning that starting from a hard assignment and letting it drift beats starting from nothing, though the margin is small on this task. **Not yet done**: rerunning on a harder/less-saturated task, where there's actual headroom for the mechanism to show a positive effect rather than just "not harmful."

**Tier 2 — shared expert + explicit outlier handling**, both pulled from DCST §4.2/§4.6. `SparseMoEFeedForward` now supports `n_shared_experts` (always-active experts summed unconditionally into the output, alongside the top-k routed ones — DCST's "shared group," also DeepSeekMoE's design) and `route_noise_to_shared_only` (a DBSCAN-noise-labeled token gets its routed-expert weight zeroed entirely, relying only on the shared expert(s), instead of silently taking whatever the unbiased gate prefers — adapted from DCST's dense-fallback-for-outliers idea; adapted because we don't have a literal dense path to fall back to, see Design notes). Gradient-checked at both the standalone-layer and full-model level, including the specific case where the outlier branch actually engages (confirmed, not just present-but-unexercised code).

**Tier 3 — periodic reclustering for the MoE-bias Judge specifically** (`judge_reclustering.py`, DCST §4.7) — NOT the confidence Judge, which deliberately still fits once post-training (see above: it wants to describe the final, stable model; the MoE-bias Judge actively shapes training, same genre as DCST's problem, so it's the one that should move). `maybe_refit_judge()` fits a candidate Judge, decides whether to apply it via a stability guard, and if applied, warm-starts `judge_bias_table` by nearest-centroid matching old clusters to new ones (two explicit simplifications from DCST's literal recipe: nearest-centroid instead of Hungarian optimal assignment, and resetting `cluster_running_loss` instead of a literal LR warmup, since there's no LR schedule to hook into).

A real bug was caught and fixed while testing this, not a one-off: the first stability-guard design compared "old judge's nearest-neighbor label" against "new cluster's centroid-matched label" directly, which has a blind spot — when a genuinely NEW cluster appears, both measurements can independently fall back to the same nearby old cluster, making a real structural change look like zero change (caught via `judge_reclustering_test.py`'s "a 4th blob appears" case, which the naive version silently failed to flag). Fixed by comparing the two label sets with **Adjusted Mutual Information** instead — a partition-level comparison with no such asymmetry. A separate, smaller known limitation (documented, not fixed): nearest-centroid matching has no distance cutoff, so a genuinely novel cluster still inherits a stale bias from whatever old cluster happens to be nearest, rather than starting fresh — the credit-update mechanism keeps adjusting from there regardless, so this affects warm-start quality, not correctness.

## Design notes / what's deliberately simple right now

- Decoder-only, causal self-attention only — no encoder side, no cross-attention. Chosen because next-token prediction is the most direct fit for later LLM-segment work, and it's the smallest architecture that's still a real language model.
- Plain SGD (`sgd_step`) still used everywhere except `train_tinyshakespeare.py` — the toy synthetic tasks converge fine without Adam; added `optim.py`'s `Adam` specifically for the real baseline test, not retrofitted everywhere preemptively.
- `CharTokenizer` (character-level) exists now, but only for `train_tinyshakespeare.py` — nothing else in this codebase uses real text yet (toy tasks operate on integer ids directly).
- No model save/load for `GPTStyleTransformer` yet (TCA's `.nexseg` has no analog here) — the trained tiny-shakespeare model exists only in that run's process memory; sampling/generating text from it would need this built first.
- `trace.py`'s records currently capture norms/entropy, not full raw activation dumps by default (attention weights are the one full-tensor exception, since they're the main "what is this head doing" signal) — extend `record()` calls in `attention.py`/`transformer.py` as specific interpretability questions come up, rather than logging everything unconditionally.
- `DistributionJudge.query_batch()` is brute-force pairwise distance — fine at toy/test scale, would want a KD-tree or similar for a training set too large for an O(N) scan per query.
- `SparseMoEFeedForward` computes every expert densely (see above) — fine for a small research model, not representative of production MoE's actual compute profile.
- DCST ideas deliberately NOT adopted: real sparse compute (block-sparse GEMMs, actual FLOP/memory savings — a systems-engineering problem orthogonal to a numpy research tool), attention/conv partitioning (a separate, large piece of architecture work), and a single shared cluster map driving every layer (we keep each block's Judge/gate independent — see "each layer has its own independent experts" above).
- `route_noise_to_shared_only`'s "fallback" isn't DCST's literal dense path (we're already dense everywhere) — it's "rely on the shared expert(s) only," the closest honest analog given the compute model here.
