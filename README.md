## Abstract

DragonChild is a research project exploring whether a neural network organized like a **map** — instead of like a stack of layers — can make predictions that are both accurate and easy to explain.

Most neural networks are black boxes: data goes in, a prediction comes out, and the "why" is buried in thousands of opaque weights. DragonChild instead places nodes at positions in a coordinate space and routes data between them based on geometric distance, the way a signal might hop across a network of relay stations. Along the way, each step tracks its own uncertainty, so the system can say "I'm confident" or "I'm not sure" rather than just guessing. The result is a model whose internal structure can be visualized, traced, and audited step by step.

The project is tested against a concrete benchmark — predicting student exam scores from a tabular dataset — and compared head-to-head against standard machine learning models (linear regression, random forest, gradient boosting, XGBoost, a small MLP, and a CNN) to see whether the added structure is actually worth its cost. The underlying architecture (TCA0.6.0, carried forward unchanged into TCA1.0.0) does not yet outperform a plain linear regression on this benchmark, but it shows the architecture's strengths — interpretability, modularity, and built-in uncertainty — clearly enough to be a promising foundation for tasks where those properties matter more than squeezing out the last bit of accuracy (e.g. anomaly or intrusion detection, sketched out in `TCA0.6.0/simulatedattackplan.txt`).

**Status:** `TCA2.1.0` is the current, actively developed version — see [Evolution](#evolution-detailed-history) for the full version-by-version history. `TCA1.1.2`–`TCA1.1.4` and the `visualizer/` tool exist in this repo but aren't documented below yet (a real gap in this README, not an indication nothing happened there); `TCA1.1.1` is the last version with a full writeup and remains the reference point for the `Setup`/`How it works` sections immediately below, since `TCA2.x`'s new node types and routing mechanisms are currently research/API-only — exercised directly via `SegmentHandler`/`SystemHandler` Python calls in ad-hoc scripts, not yet wired into `settings.json`/`main.py`'s CLI the way TCA1.1.1's knobs are. `TCA1.0.0`/`TCA1.1.0` and `TCA0.5.0`/`TCA0.6.0` (plus `TCA0.6.0-Analysis`) remain as the two reference lines before that. Everything before `TCA0.5.0` (`TCA0.0.1`–`TCA0.4.0`, `TCA0.4.0-E`) is historical and kept for reference only.

## Setup

```bash
pip install -r requirements.txt
```

**TCA1.1.1 (current):** everything is driven from `TCA1.1.1/settings.json` through a single CLI entry point — no notebook or hand-written script required.

```bash
cd TCA1.1.1
python main.py                 # interactive: prompts for train / infer / compare
python main.py --mode train    # train a fresh set of segments, save .nexseg files + graphs
python main.py --mode infer    # load saved .nexseg segments and evaluate a sample
python main.py --mode compare  # benchmark against the sklearn/XGBoost/CNN baselines
python main.py my_settings.json --mode train   # point at an alternate settings file
```

All model, training, logging, output, inference, and comparison options live under their own section in `settings.json` (`model`, `training`, `logging`, `output`, `infer`, `comparison`); anything omitted falls back to the defaults baked into `Settings.py`. Trained segments are persisted to `segment_<i>.nexseg` files so `infer` mode can run without retraining (the JudgeNode's cluster weighting isn't persisted yet, so reloaded segments are weighted equally at inference time).

**TCA0.6.0 / TCA0.6.0-Analysis (prior line):** run a model directly, or use the notebooks.

```python
from SystemHandler import SystemHandler

from SegmentHandler import SegmentHandler
```

Open the evaluation notebooks in `TCA0.6.0-Analysis/` (`v12Analysis.ipynb`, `SegmentHandlerAnalysis.ipynb`) with Jupyter to reproduce the benchmark comparisons.

## How it works

TCA0.6.0/TCA1.0.0/TCA1.1.0/TCA1.1.1 share the same reference architecture (TCA1.0.0 changed packaging, not the math; TCA1.1.0/TCA1.1.1 added configurable training-dynamics knobs on top — see [Evolution](#evolution-detailed-history)). A prediction flows through five stages:

1. **PreProcessingNode** — tokenizes/normalizes the raw dataset.
2. **JudgeNode** — k-means clusters the input space into segments and routes each sample to the most relevant segment(s).
3. **SplitterNode → ProcessingNode** — within a segment, signals propagate stochastically between geometrically-positioned processing nodes, each applying a learned weight and accumulating variance.
4. **ReviewerNode** — aggregates a segment's signals into one prediction via inverse-variance weighting.
5. **HandlerNode** — combines all active segments' predictions into the final output, via `bma`, `simple_mean`, or `relevance_weighted` aggregation.

`SegmentHandler` exercises steps 3–4 alone (one segment, no routing); `SystemHandler` runs the full pipeline.

## Strengths and weaknesses

**Strengths**
- Interpretable, inspectable topology — node positions, signal paths, and variance are all traceable, unlike a typical NN's weight matrices.
- Built-in uncertainty quantification: high inter-reviewer variance is a usable "I'm not sure" signal, not just a wrong-but-confident prediction.
- Unsupervised regime discovery via `JudgeNode` k-means means segments specialize without manual labeling.
- Modular by construction, which makes it a plausible fit for tasks that want per-regime experts plus a confidence signal (e.g. anomaly/intrusion detection, as sketched in `TCA0.6.0/simulatedattackplan.txt`).

**Weaknesses**
- On the exam-score benchmark, the best `SystemHandler` configuration (MAE ≈ 9.3, R² ≈ 0.64) still trails plain Linear Regression (MAE ≈ 7.97, R² ≈ 0.73) and MLP — the architecture has not yet beaten simple baselines on this task.
- Training cost is dramatically higher than the sklearn baselines (hours vs. seconds), which is a hard sell unless the interpretability/uncertainty properties are specifically needed.
- The codebase has a history of subtle correctness bugs that quietly inflate results (the TCA0.4.0 target-leak below being the clearest example), which argues for treating any single notebook run's numbers with caution until cross-checked.

Auto mode instead derives the clip from the segment's actual hop topology (target span ÷ `num_processing_nodes ** (1/dimensions)`, i.e. the number of shells a signal must cross from splitter to reviewer), since this clip acts directly on the propagated prediction rather than a learning-rate-buffered gradient like `grad_clip`. |

| **`visualizer/`** | A browser-based tool for inspecting a trained run's segment graph, signal paths, confidence/curves, and logs, plus a live custom-query tab — undocumented here beyond this pointer; see the folder itself. |
| **TCA2.0.0** | First cut of a new major line, exploring "differing segment task capabilities" as a track separate from the shipped TCA1.1.x default (TCA1.1.x is untouched by any of this). `ProcessingNode` was split into a shared geometric/routing base class plus concrete, swappable compute types: `RegressionProcessingNode` (a numpy-vectorized version of the original weighted-sum-of-features forward pass — identical math, no accuracy change, a real speed win specifically on wide/one-hot-heavy feature spaces) and `BayesianProcessingNode` (a Kalman-filter-style posterior update in place of flat-learning-rate gradient descent, with a real propagated `posterior_var` instead of the old crude `variance += abs(delta)` proxy). Bayesian nodes were tested extensively — across training-sample size, label-noise level, and training duration — without finding a confirmed accuracy edge over Regression nodes on this benchmark; kept as a genuinely different, validated learning paradigm, not as a proven win. `CompressionNode` (a per-signal feature-relevance filter) was tested on this tabular benchmark and found no speed win and a real accuracy cost; kept as scaffolding for a future NLP-style segment with genuinely high-dimensional, sparse features, where the same test is expected to look very different. `ConfidenceEstimator` replaces the fixed `1/variance` reviewer-confidence heuristic with a small trained model (predicts a signal's actual error from its accumulated variance and hop count, gradient-trained against real per-signal error) — a real, consistent accuracy improvement over the old heuristic when used as the reviewer-level aggregation weight. `SystemHandler.run_infer_adaptive_loop()` adds confidence-triggered inference retry (bounded by `max_loops`) as a cheaper alternative to always paying for a fixed-size ensemble. |
| **TCA2.1.0** *(current)* | Four new routing mechanisms were tested on top of TCA2.0.0's node types, head-to-head and multi-seed — only one held up. `routing_mode='similarity'` (route by cosine similarity between a signal and a candidate node's own weight vector) and confidence-gated routing temperature (use `ConfidenceEstimator`'s confidence mid-route as a softmax temperature, exploring more when uncertain) both carried a real cost without a reliable accuracy benefit; `similarity`'s effect flipped sign across repeated tests at different scales and should be treated as unresolved, not confirmed either way. A hop-count-relative "lingering escape" was added to stop confidence-gated exploration from feeding back on itself (more exploration → more hops → higher variance → lower confidence → more exploration); confirmed working via unit test, but not sufficient on its own to make the temperature mechanism worth keeping. The mechanism that held up at every scale tested: `Components/ArchetypeRouter.py` — a held-out routing-training subset runs through a one-time exploration phase (a few repeated stochastic passes per sample, reusing the architecture's own routing stochasticity), and real observed error — not a heuristic proxy — trains a per-(KMeans-cluster, edge) routing preference, applied as a multiplicative factor on top of whichever base routing is active. Confirmed through the real, multi-segment `SystemHandler`/`JudgeNode`/`HandlerNode` pipeline (not just one isolated segment) on the full 20,000-row benchmark, 3 seeds: R² 0.388→0.440, MAE 12.26→11.68, for a one-time training-side cost under 1% of total training time (full breakdown in [Archetype routing: pros and cons](#archetype-routing-tca210-pros-and-cons)). Two real, previously-hidden bugs were found and fixed while building this: several single-segment test scripts (not the shipped training path) were silently evaluating every one-hot-encoded categorical feature as a constant `0.0` at test time, since raw rows were passed straight to `segmentInfer()` instead of through the fitted preprocessor first; and archetype routing's `cluster_id` was being recomputed via a KMeans-predict call at *every hop* instead of once per signal — a real ~2.8x inference-time cost at full-system scale, fixed by caching it on the signal object (confirmed bit-for-bit identical predictions before/after the fix, 2.15x eval-time speedup). |

## Archetype routing (TCA2.1.0): pros and cons

**Pros**
- Real, reproducible accuracy improvement, confirmed at the full multi-segment-system level (not just an isolated segment) across two independent training runs of three seeds each: R² 0.388→0.440, MAE 12.26→11.68 on the exam-score benchmark.
- Trained on real observed error, not a heuristic proxy — directly avoids the failure mode that sank `similarity` routing (a plausible-sounding signal with no proven tie to actual correction quality).
- Training-side cost is close to free: the one-time exploration phase adds well under 1% to total training time (~5s on a ~670s run).
- Reuses existing machinery almost entirely — the architecture's own routing stochasticity for exploration, `KMeans` for cheap sub-clustering, a proportional (not winner-take-all) credit rule — no new gradient estimator, no architecture change.
- The benefit concentrates in specific segments rather than spreading evenly across all of them, which is itself useful: a deployment that only wires the best-performing segment(s) captures nearly all of the win at a fraction of the ongoing inference cost (confirmed via a full 2⁴-subset sweep, not just a "how many" count).

**Cons**
- Real, measurable inference-time cost: even after the `cluster_id`-caching fix, ~33% slower per prediction than the baseline (down from ~2.8x before the fix).
- Needs a held-out routing-training subset per segment — a genuine (if small) data-budget cost, and a segment with too few assigned rows can't support it at all (falls back to a no-op rather than crashing, but silently gets no benefit).
- The exploration phase's credit assignment is a crude, uniform-per-path-edge approximation, not formal policy-gradient training — it works, but there's real room for it to be more precise.
- Doesn't generalize predictably: which segments benefit, and by how much, isn't knowable in advance — a new dataset or task needs its own confirmation run, not just "turn it on."
